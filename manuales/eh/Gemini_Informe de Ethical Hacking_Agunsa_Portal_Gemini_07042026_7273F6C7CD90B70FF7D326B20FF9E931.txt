Metodología de Trabajo
Para la categorización y registro de vulnerabilidades detectadas, se utiliza la metodología OWASP (Open
Worldwide Application Security Project), la cual es aplicada tomando en cuenta su versión más
actualizada para cada tipo de revisión o pentesting realizado (Web, Mobile, API). A su vez, para
complementar esto y dar un enfoque más específico, también se utilizan las definiciones descritas en
el CWE (Common Weakness Enumeration). Estos son frameworks mundialmente conocidos y
aceptados en el ámbito del manejo y reporte de vulnerabilidades informáticas, los cuales permiten dar
un mayor entendimiento de las mismas.
Criterios de clasificación del riesgo
Para realizar la clasificación y puntuación de las vulnerabilidades detectadas, se utiliza el sistema de
puntuación CVSS v4.0 (Common Vulnerability Scoring System), éste es un framework abierto que
permite capturar las principales características de una vulnerabilidad y genera un valor numérico que
refleja el nivel de severidad, así como también una representación textual del score, esto se traduce a
una representación cualitativa (crítico, alto, medio y bajo) que permitirá ayudar al equipo técnico a
priorizar el proceso de gestión de vulnerabilidades. Los valores evaluados se muestran a continuación:

Referencias: https://www.first.org/cvss/calculator/4.0 Beneficios del CVSS:
A. Alineado con la norma PCI DSS.
B. Estandariza la calificación de la vulnerabilidad.
C. Prioriza el riesgo.
D. Considera el impacto directo sobre el objetivo, así como el impacto subsecuente en otros sistemas.

C01: Escalamiento de privilegios vía manipulación de respuesta de login
Descripción:
Se ha identificado que la aplicación devuelve en la respuesta del endpoint de autenticación
toda la información de autorización del usuario (por ejemplo parámetro admGlobal y el objeto
completo de privilegios). El frontend confía ciegamente en estos datos para determinar los
permisos del usuario actual, sin que el backend realice validaciones adicionales de
autorización en las peticiones posteriores (usando el token devuelto).
En ese sentido un atacante con una cuenta de usuario normal puede interceptar y modificar la
respuesta de login (usando Burp Suite Match & Replace o cualquier proxy MITM) para elevar
sus privilegios a nivel de administrador (admGlobal: true + todos los privilegios de GEMINI).
Esto demuestra que la lógica de control de acceso está parcialmente implementada en el
cliente en lugar de estar enforced server-side.

C03: Apropiación de cuenta completa (ATO) en cualquier cuenta mediante
cadena de vulnerabilidades
Descripción:
Se ha identificado una cadena de vulnerabilidades que, combinadas, permiten a un atacante
apoderarse completamente de cualquier cuenta del sistema. El ataque se puede ejecutar por
dos vías independientes:
Opción A — Fuerza Bruta sobre endpoint de autenticación
•

•
•

•
•

La API GET /api/v1/usuarios, accesible con un token de usuario
administrador, se devuelve el listado completo de usuarios registrados
incluyendo login, nombre, email y rol de administrador.
Con el listado de usuarios obtenido, se realizó un ataque de fuerza bruta
sobre el endpoint POST /api/v1/login utilizando contraseñas comunes.
El sistema no implementa bloqueo efectivo ni CAPTCHA, permitiendo iterar
sobre todos los usuarios. Se obtuvo acceso exitoso con el usuario
'avenegas'.
Una vez autenticado, el atacante puede operar dentro del sistema con
todos los privilegios del usuario comprometido.
Esta opción es apropiación de cuenta parcial, debido a que el usuario
podría recuperar su contraseña y el atacante podría pedir perder el acceso.

Opción B — Modificación de email + secuestro vía recuperación de contraseña (ATO
Completo)
•

•

•
•

•

La API GET /api/v1/usuarios, accesible con un token de usuario
administrador, se devuelve el listado completo de usuarios registrados
incluyendo login, nombre, email y rol de administrador.
La API PUT /api/v1/usuarios, accesible con un token de usuario
administrador, permite modificar los datos de cualquier usuario objetivo,
entre ellos su campo 'email' por uno controlado por el atacante.
A continuación, el atacante invoca el flujo de recuperación de contraseña
ingresando el login de la víctima.
El sistema envía el código de recuperación de 6 dígitos al email que ahora
controla el atacante y con ese dato puede establecer una nueva
contraseña y toma control total e irreversible de la cuenta.
Esta opción es apropiación de cuenta total, debido a que el usuario podría
recuperar su contraseña y el atacante podría pedir perder el acceso.

Conclusiones
En el marco de las pruebas de seguridad realizadas sobre el Portal Gemini, se identificaron 8
vulnerabilidades que podrían comprometer la seguridad de la aplicación y la protección de la
información procesada.
Los hallazgos detectados se relacionan principalmente con:
•
•

•
•
•

Escalamiento de privilegios y apropiación completa de cuentas (ATO) mediante
manipulación de respuestas de login y cadenas de vulnerabilidades.
Falta de controles de autorización y referencia insegura a objetos (IDOR), permitiendo
acceso no autorizado, ejecución de funciones privilegiadas y descarga masiva de
información.
Exposición de credenciales AWS IAM con acceso Read + Write a buckets S3 que
almacenan información sensible.
Consumo inseguro de APIs para la gestión de usuarios y roles del sistema central de
seguridad.
Inyección HTML en generación de PDFs y revelación de rutas internas por mal manejo de
errores.

Estas vulnerabilidades podrían permitir la alteración de datos, el acceso indebido a
información sensible o la enumeración de recursos internos, impactando la confidencialidad,
integridad y disponibilidad del sistema.
Se recomienda implementar las medidas de mitigación descritas en el presente informe y
realizar las validaciones técnicas correspondientes una vez aplicadas. Asimismo, se sugiere
mantener coordinación con el equipo de desarrollo para verificar la correcta implementación
de los controles y ejecutar una revalidación posterior que confirme la remediación efectiva de
los hallazgos.
